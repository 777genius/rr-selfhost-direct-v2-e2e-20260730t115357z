## SR1 — P2: broker construction failure retains the ledger lock

Frozen `broker.mjs:18–22` acquires and writes the exclusive process lock before loading and validating the ledger. Only the later persistence failure at line 25 closes the handle and removes the lock. Malformed JSON, invalid schema, or a ledger read failure therefore rejects before `createBroker` returns its server. Frozen `serve.mjs:74` never assigns `server`, so its catch/shutdown cannot clean up this owned lock.

Independent execution of the actual frozen `boot` confirmed the failure without opening sockets: an invalid-schema ledger rejects with `Invalid ledger`; its lock still exists; correcting the ledger and retrying in the same process rejects with `EEXIST`. This is an inherited transitive defect, not a change introduced by the serve diff. It turns a recoverable initialization error into manual stale-lock recovery and leaves the opened handle outside cleanup. Put all initialization after successful lock acquisition under cleanup on exception, preserving intentional crash fail-closed behavior. Add invalid-JSON/schema/read-failure regressions alongside the existing partial-listen rollback test. Evidence: `independent.test.mjs` and `verification/independent.tap`, 1 pass, 0 fail, 0 skip; passing means the defect was reproduced, not repaired.
