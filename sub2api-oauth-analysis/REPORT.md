## Thin fork plan and ownership

Use existing `OAuthRefreshAPI` / `AccountRepository` / scheduler outbox seams, scoped to these OAuth lifecycle paths. Existing conditional SQL completion pattern at `account_repo.go:1592–1645` demonstrates atomic update plus outbox; do not transplant its narrower predicates without lifecycle/admin checks. No general distributed coordination platform is needed.

1. **Repository owner:** introduce a database-owned per-account lifecycle revision and a small attempt record (owner ID, expected revision, pending/uncertain state). Short transactional claim checks active/schedulable account, expected complete document/routing identity and absence of pending attempt; commits ownership before issuer HTTP. Both request and background use the same claim regardless of Redis availability. Existing claim causes bounded waiting or protected rejection, never another issuer request. No database row transaction remains open across HTTP, so admin reconnect/disable can proceed.
2. **Lifecycle service owner:** complete only the matching attempt/revision, with conditional credential update plus outbox in the same transaction. Success rereads committed row. Confirmed invalid_grant conditionally excludes only matching state. A returned rotated result with failed persistence leaves ownership pending/uncertain and blocks new work; a lost acknowledgement rereads completed attempt plus exact durable successor before declaring success. Timeout/crash after claim must not expire into replay: wait/reconnect/manual resolution is required when consumption is unknown. Persistence-only retry may use retained result while the same CAS still holds. A CAS miss caused by reconnect returns its latest state; disable remains disabled.
3. **Admin/repository owner:** reconnect and disable must atomically advance the same lifecycle revision and fence pending completion. Disable preserves consumed/uncertain attempt history; ordinary re-enable must not clear it or replay old state. Reconnect supersedes it only with a newly committed replacement credential document. Patch field intent under current-row lock/CAS; do not save a previously read complete account. Actual admin `internal/service/admin_account.go:574–575,642–656,826–827,878–881` and `account_service.go:317–332,360–379` read then write an account; repository `account_repo.go:542–547` also writes credentials/status from that snapshot. Guard both orderings (refresh then stale admin disable; reconnect/disable then late refresh), including bulk/lower repository entry points. Cache invalidation/outbox belongs to the mutation transaction; Redis publication follows commit.
4. **Cache/request owner:** assign revision in PostgreSQL (`revision=revision+1`), not client clocks. Existing `_token_version=UnixMilli()` (`oauth_refresh_api.go:295`) can collide; `CheckTokenVersion` (`token_cache_invalidator.go:87–120`) accepts equality, lower database versions and failed rereads. The reconnect fixture sets a version one hour ahead (`oauth_lab_fixture_test.go:166–171`): it proves overwrite despite changed document, but does not prove real admin version advancement. Store lifecycle revision with access-cache entries; validate durable eligibility/revision before selection, including cache hits, and reject unavailable/mismatching state. Atomic Lua revision checks cover scheduler full/meta writes, access-cache writes and deletion tombstones; reject older revisions even after deletion. Compare big revisions as exact integers/decimal strings without Lua floating-point rounding. Keep durable admission checks because delayed invalidation/outage cannot guarantee instantaneous Redis coherence.
5. **Redis cache owner:** owner-token compare-delete prevents predecessor erasure; acquisition/release handles must identify each lease, not a process-local map keyed only by account. Redis lease becomes an optimization over durable ownership, not permission to replay. Preserve bounded detached cleanup. Durable pending attempt protects expiry, Redis reset and process crash.

Implementation ownership/budget (estimates, not authored changes): `internal/service/oauth_refresh_api.go` lifecycle branches **80–120 added/changed lines**; `internal/repository/account_repo.go` scoped claim/completion/admin field-intent methods **120–180**; new backend migration/attempt storage and account revision mapping **40–80**; `openai_token_provider.go`, `token_refresh_service.go`, `token_cache_invalidator.go` typed errors/admission **70–110**; `scheduler_cache.go`, `gemini_token_cache.go` atomic revision/owner scripts **60–100**; admin/account update call sites **30–60**. Target roughly **400–650 production lines**, split by these owners; review repository entry-point coverage before setting a firm cap. No UI, unrelated lifecycle or dependency overhaul.

**Outage tradeoff:** fail closed on Redis locking error is the smallest immediate containment, but intentionally removes the current local-outage success behavior (and requires its oracle to assert protected rejection rather than eight successes). PostgreSQL locking/claim fallback preserves availability when PostgreSQL works. A fallback used only by Redis-error workers is unsafe: a Redis-success worker would use a different mutex. All workers must share the PostgreSQL ownership domain. Session advisory lock across HTTP serializes healthy processes, but connection/process loss still permits replay after uncertain consumption; combine it with durable attempt state, or prefer the short row claim above. Never silently fall back to local-only ownership when PostgreSQL fails.

## Independent oracle revisions and regression gates

Current TTL test waits for **second issuer entry** before releasing the first (`oauth_lab_lifecycle_test.go:189,195`); outage race does the same (`:234,240`). A correct fix suppressing second requests will exhaust the barrier/timeout. This is a **test orchestration artifact**, not justification for accepting a second request. The normal contention and background-order tests also depend on Redis `lock_contended` events; a changed coordination backend needs corresponding real ownership observations.

Minimal oracle revision: after observing expiry/outage and releasing contender, multiplex (a) any unexpected issuer entry, (b) child protected-rejection result, or (c) an observer event for actual PostgreSQL ownership contention. Observation hooks must report actual repository outcomes, not manufacture success. Unexpected issuer entry is always FAIL, release its gate for cleanup. A safely waiting owner is acknowledged, then release the first issuer reply immediately; never wait for contender completion while holding that reply. Finish under bounded deadlines; successful contender must use independently committed current state, or return protected error with zero resource HTTP. Final **issuer <=1**, one rotation when first succeeded, **no A0/unknown bearer**, and independent PostgreSQL/Redis revision/eligibility assertions remain mandatory. Under fail-closed Redis outage the first may also reject, so zero rotations/requests are valid only for that explicitly selected policy, not a silently weakened availability contract.

Split lease-release correctness into a separate real-Redis contract: acquire predecessor handle, observe expiry, acquire distinct successor handle without sending another issuer request, release predecessor, independently GET/PTTL successor and confirm unchanged owner/live lease. This catches unconditional DEL while allowing durable refresh exclusion to do its job.

Keep all 12 original receipts/verdicts intact. New corrected-oracle executions must use separate receipts/input hashes. Add only meaningful independent contracts: two admin orderings with same-millisecond/reversed clocks and no caller revision; delayed old full/meta/access-cache write after disable/reconnect and deletion; mixed Redis-success/error processes using one durable owner; child termination after consumption before completion (no replay after restart); failed completion plus lost-ack exact-result recovery; terminal invalid_grant racing reconnect (new revision remains usable); direct selector with primed old cache after disable/revocation (not fixture scheduling gate). Existing six working cases remain availability/regression gates under PostgreSQL ownership. None is marked green until actually executed.
