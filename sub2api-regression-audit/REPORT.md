## E06: deliberate accounting drain, with a flawed Responses cancellation observation

The staged `backend/internal/service/gateway_usage_billing.go:573` and `:583` detach streaming/upstream contexts with `context.WithoutCancel`, returning a no-op release function. `openai_gateway_forward.go:1042` uses the detached context for native Responses. `openai_gateway_response_handling.go:246` explicitly marks client disconnect and continues upstream drain for billing; write/flush failures suppress further downstream writes rather than immediately cancelling the provider request. Native compatible Messages uses `detachStreamUpstreamContext` at `openai_gateway_messages_anthropic_native.go:96`, closes the response body on function exit, and keeps parsing usage after writer failure at `:470`. Its scanner queue is 16 lines; configured data-interval timeout can terminate incomplete usage. These are deliberate accounting choices. Disabling client retries or aborting the broker fetch does not undo them.

There is an important timing weakness in the older evidence:

- `first-20260930-faults-fixed.json`, E06-M: first Messages frame reached the client in 4 ms; after the lab's approximately 1.2 s observation, the synthetic upstream was still open. This supports failure of prompt upstream transport cancellation at that boundary. It does not quantify complete drain or resource release.
- `first-20260930-remaining.json`, E06-A: upstream finished normally at 6003 ms, while the client first-data cancellation was reported at 6011 ms. `run.mjs:111` cancels on its first downstream data chunk. The tiny initial Responses frames can remain buffered in the engine. This receipt **does not prove six seconds of upstream work after client cancellation**. The earlier E06-A cases with zero upstream requests also do not exercise cancellation.
- A mock `finish` event means its response was handed to its transport, not that a real provider completed billable inference. Socket close is a local transport observation; remote stop-spend remains provider policy.

The corrected experiment needs independent timestamps for upstream first-frame flush, downstream socket destroy, engine upstream close, mock completion and capacity availability. Send a valid early native frame large enough to cross buffering, flush it, wait for client acknowledgement, then destroy the client while the provider fixture remains blocked. Exercise both protocols, plus broker revoke/expiry, and separately test cancellation before first output. The oracle requires `t_cancel < t_upstream_terminal`; otherwise mark the attempt inconclusive, never PASS. Observe for a fixed bound, then intentionally release the fixture and inspect final usage. Use a second synthetic request to measure slot reuse and simultaneous provider work; a released local slot alone cannot establish remote cancellation.

## Is an opt-in native API-key abort safe?

**Not as a forwarding-only toggle.** No supported abort-on-disconnect setting was found in the inspected gateway context helpers/config. Existing stream interval/keepalive settings control silence, not cancellation policy; a provider producing continuously can keep a drain alive. This conclusion is limited to the inspected tree and requires pin verification.

An account-scoped option could be viable for explicitly configured native API-key providers, defaulting to existing drain behavior and excluding OAuth/other routes. Its minimal review scope would be account extra/config validation, the two native request-context creation paths and stream handlers, result metadata, Responses/Messages usage submission, slot cleanup and the existing usage/billing/reservation boundary. Do not globally change `WithoutCancel`, which also protects billing persistence and cleanup. The existing request builder calls the no-op release immediately after building a request; replacing it with a real cancel without changing lifetime would cancel a healthy request before forwarding.

Current handler code (`openai_gateway_handler.go:859` onwards) submits partial usage for disconnect/error results as well as successful forwarding; detached billing (`gateway_usage_billing.go:565`) protects post-request writes. Inflight reservation release and final debit are separate. Aborting before terminal usage can lose output/reasoning/cache tokens and provider effects. Partial or absent usage must be explicitly marked incomplete/unknown, retained for reconciliation, and excluded from any assertion of exact final debit or zero spend. Never fabricate usage, refund as though no work occurred, or report successful review. Exact accounting is safe only with a provider-supported final usage/reconciliation contract; otherwise expose uncertainty or keep drain. Usage persistence must be idempotent and independent of the cancelled request context.

Minimal *future* behavioral tests, after checking existing tests for overlap:

1. Default policy: upstream remains readable after client cancel and terminal usage is persisted once; healthy SSE bytes/tool IDs are unchanged.
2. Opt-in Responses and Messages: provider transport closes within the agreed local bound, no second request starts automatically, handler/scanner exits, slot is released once, partial usage remains incomplete and no invented successful terminal appears.
3. Race cancel vs terminal: one usage row/final debit and one slot release, including terminal received just before downstream failure.
4. Cancel before usage, late usage persistence, worker queue/persistence failure: no false zero charge, silent refund or retry after uncertain effect. Capture pending reconciliation state.
5. OAuth/default accounts remain on current policy; disabling the option restores default behavior.

Existing disconnect/drain tests such as `openai_gateway_chat_completions_raw_test.go` concern a different route. Reuse relevant native tests where available; do not duplicate raw-Chat tests and call that native Responses coverage. No engine policy was implemented here.

## E07 / G05: engine memory remains unproved

The 8.39 MB replay completed in 29151 ms with one upstream request and client/control RSS delta 27684864 bytes. The lab explicitly collects response chunks up to 12 MiB, so that RSS is partly observer retention. Engine post-load 60.07 MiB is not peak memory. The 485-request soak proves only the recorded workload, not a streaming memory envelope.

A fixed scanner/channel bound is also insufficient. Inspect full data frames, multiline JSON document assembly, pending frames and output accumulators: staged Responses has a 4 KiB writer, scanner/document scanner, asynchronous queue and `BufferedResponseAccumulator` at `openai_gateway_response_handling.go:344`; native Messages queues 16 lines. Slow writes can retain these structures and connections. Broker `native-errors.mjs` limits individual frames to 2 MiB but temporarily concatenates chunks; a per-frame bound does not bound whole-system memory.

Use actual engine process RSS plus cgroup peak, 100 ms samples, baseline/post-drain, worker/goroutine and socket counts. Run finite 8/32/64 MiB valid streams with a streaming client that discards consumed bytes, both protocols, concurrency 1/5/20. Include comment-only pressure, text deltas, large tool results and multiline/near-limit frames; the old comment fixture misses accumulator growth. Predeclare envelope and wall-time limits (replay plan), count all provider attempts, and verify capacity recovery. A payload-size-dependent rise or retained workers makes the test red. Missing engine telemetry means NOTRUN, not PASS.
