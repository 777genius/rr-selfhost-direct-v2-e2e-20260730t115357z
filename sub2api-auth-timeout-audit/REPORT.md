## Explicit 300-second assessment

Keep 300 seconds explicitly declared in configuration and receipt metadata, with unchanged source/image and native gates. A roughly 150-second request could fit this budget if enough lease remains; it cannot fit the earlier 120-second budget. That is a useful single-variable experiment, not an observed successful outcome here. At request start, effective allowance is still `min(300000, lease remaining)`: a nominal five-minute lease cannot give a full 300-second request after grant/setup overhead, and multiple tool turns/retries must share the same remaining lease. Raising request timeout cannot extend grant expiry. Native first-output/cancellation deadlines, original Redis and RSS acceptance remain independent gates.

The parent's fresh run must retain normalized identity/terminal/tool-read/numeric reproduction evidence, deployed configuration and source/image bindings, before/after/drained usage attribution, and owned cancellation/cleanup outcomes. This child will neither poll nor rerun it. A PASS would support only that tested bounded path; models/providers beyond the tested mappings remain unknown.

## Smallest proposed contract for jobs longer than five minutes

Recommend one explicit bounded access lease, separate from the minting JWT lifetime, for jobs bounded to at most 15 minutes. Validate a currently valid GitHub JWT only at mint, preserve its immutable identity checks, and authorize a server-owned capability until `min(mint + approved job budget, mint + 15 minutes)`. The approved budget must come from trusted job policy, not a caller-selected extension. The lease may intentionally outlive JWT exp; this is a proposed authorization-policy change, not the current implementation or an implied permission to change TTL now. Keep the current 15-minute ceiling, request/concurrency counters, scoped model/protocol/workspace/session, revocation, membership checks, fail-closed replay/persistence, disconnect cancellation and native gates. JWT expiry still blocks any new exchange using that expired JWT; capability expiry independently blocks and aborts work.

Expose/consume the absolute lease deadline in the trusted launcher, reject insufficient remaining lifetime before expensive dispatch, and clip each request to the lease and trusted outer job deadline. A 300-second per-request budget stays explicit. Define uncertain timeout outcomes as possibly billed; require effect/usage inspection before retry, bounded attempts, and no automatic broker replay. Client retry behavior needs an explicit bound, particularly for Claude. Expiry or disconnect must retain owned cleanup/drain evidence.

This avoids introducing a renewal service for a job already bounded within 15 minutes. It does not support arbitrary-duration jobs. If JWT-capped authority is a mandatory policy, this option is unavailable: authenticated renewal with stable identity/session/counters, fresh JWT verification, a fixed maximum job horizon, revoke/replay rules, expiry races and client capability rotation would be required. Current exchange cannot serve as that renewal endpoint. Jobs beyond 15 minutes require a separately approved contract and are outside this recommendation.

Provisional work estimate for only the bounded independent-lease option: **60–120 changed production lines plus 100–180 test lines**, spanning trusted broker mint/admission policy and launcher deadline handling, with deterministic boundary/replay/authority tests and bounded retry-policy checks. This is an inspection-based estimate, not a diff or commitment; a newly required native-client token-rotation interface, renewal, distributed scheduling or credential platform is excluded. Existing sealed harness/workflow bindings would need parent-managed resealing and genuine acceptance. No such implementation was performed.
